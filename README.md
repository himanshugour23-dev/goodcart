# GoodCart

GoodCart is a local supermarket offers platform. I built it to give shoppers one simple place to discover active discounts from supermarkets in their city, while giving supermarkets a small and secure API for publishing offers.

The project focuses on three core actions:

1. A supermarket registers and receives a private API key.
2. The supermarket uses that key to publish time-limited offers.
3. Anyone can search and browse currently active offers.

The frontend is browse-only at the moment. Supermarket registration and offer publishing are available through the documented API endpoints.

## Product overview

The public home page lets shoppers:

- Search offer titles and descriptions.
- Filter offers by city.
- See the supermarket name, location, discount, and expiry date.
- Browse results page by page.
- Receive loading, empty-result, and error states.

Only offers that have started and have not expired are displayed. Offers that expire soonest are shown first, so shoppers see the most time-sensitive deals at the top.

## Architecture

GoodCart is a small full-stack Next.js application. The frontend, backend API, validation, and database access live in the same project.

```text
Browser
   |
   | GET /api/offers?q=...&city=...
   v
Next.js App Router
   |
   | Parameterized SQL queries
   v
Neon PostgreSQL
```

Supermarkets publish offers through a protected route:

```text
Supermarket system
   |
   | POST /api/supermarkets/{id}/offers
   | Authorization: Bearer <api-key>
   v
Next.js API route
   |
   | Hash API key and verify supermarket ownership
   v
Neon PostgreSQL
```

### Main architectural choices

- **Next.js App Router:** I use Next.js for the user interface and server-side API routes.
- **React client page:** The home page manages search state, loading state, pagination, and API responses in the browser.
- **Neon PostgreSQL:** I use PostgreSQL as the source of truth for supermarkets and offers.
- **Parameterized SQL:** Database values are passed through Neon’s tagged-template API instead of being concatenated into SQL strings.
- **Zod validation:** Write endpoints validate request bodies before attempting database inserts.
- **Database constraints:** PostgreSQL provides a second layer of protection for uniqueness, relationships, discount ranges, and date ranges.
- **API-key authentication:** Each supermarket receives its own API key. The database stores only a SHA-256 hash of that key.

## Database design

The database schema is defined in `db/schema.sql`.

### `supermarkets`

| Column | Purpose |
| --- | --- |
| `id` | UUID primary key generated by PostgreSQL |
| `name` | Public supermarket name |
| `email` | Contact email; unique across supermarkets |
| `city` | City used by the public filter |
| `api_key_hash` | SHA-256 hash of the supermarket API key |
| `created_at` | Registration timestamp |

### `offers`

| Column | Purpose |
| --- | --- |
| `id` | UUID primary key |
| `supermarket_id` | Foreign key pointing to the owning supermarket |
| `title` | Public offer title |
| `description` | Optional offer details |
| `discount_percent` | Integer from 1 to 100 |
| `starts_at` | Time at which the offer becomes visible |
| `ends_at` | Time at which the offer stops being visible |
| `created_at` | Offer creation timestamp |

Each supermarket can publish many offers, but every offer belongs to one supermarket. The foreign key uses `ON DELETE CASCADE`, so deleting a supermarket also deletes its offers.

The schema also includes indexes for active-date filtering, supermarket lookups, and city filtering. The database constraint on `ends_at` ensures that an offer cannot end before it starts.

## Request and data flow

### Browsing offers

1. A shopper enters a search term or city on the home page.
2. The browser sends a request to `GET /api/offers`.
3. The API normalizes and limits query parameters.
4. PostgreSQL filters for offers where:
   - `starts_at <= NOW()`
   - `ends_at > NOW()`
   - The title or description matches the search text, if supplied.
   - The supermarket city matches the city filter, if supplied.
5. The API returns the matching offers and pagination metadata.
6. The page renders the results as offer cards.

The response includes:

```json
{
  "offers": [],
  "pagination": {
    "page": 1,
    "limit": 12,
    "total": 0,
    "totalPages": 0
  }
}
```

### Registering a supermarket

The registration route accepts:

```http
POST /api/supermarkets
Content-Type: application/json
```

```json
{
  "name": "Green Basket",
  "email": "offers@greenbasket.example",
  "city": "Bhopal"
}
```

The route:

1. Validates the name, email, and city with Zod.
2. Generates a random API key beginning with `sk_`.
3. Hashes the API key with SHA-256.
4. Stores the supermarket and hash in PostgreSQL.
5. Returns the new supermarket and the original API key.

The original key is returned only during registration. It is not stored and cannot be recovered later.

Successful registration returns HTTP `201`:

```json
{
  "supermarket": {
    "id": "SUPERMARKET_UUID",
    "name": "Green Basket",
    "email": "offers@greenbasket.example",
    "city": "Bhopal",
    "createdAt": "2026-10-23T00:00:00.000Z"
  },
  "apiKey": "sk_...",
  "note": "Save this API key now. It will not be shown again."
}
```

### Publishing an offer

The publishing route is:

```http
POST /api/supermarkets/{SUPERMARKET_ID}/offers
Authorization: Bearer YOUR_API_KEY
Content-Type: application/json
```

Example body:

```json
{
  "title": "Fresh fruit weekend",
  "description": "Save on selected seasonal fruit.",
  "discountPercent": 20,
  "startsAt": "2026-10-22T00:00:00.000Z",
  "endsAt": "2026-10-28T23:59:59.000Z"
}
```

Before inserting the offer, the API:

1. Validates the supermarket UUID.
2. Reads the Bearer token from the `Authorization` header.
3. Hashes the supplied key.
4. Checks that the hash belongs to the supermarket ID in the URL.
5. Validates the offer body.
6. Inserts the offer using parameterized SQL.

This prevents one supermarket from publishing an offer under another supermarket’s ID.

## API reference

### `POST /api/supermarkets`

Registers a supermarket.

- Authentication: not required.
- Success: `201 Created`.
- Invalid data: `400 Bad Request`.
- Duplicate email: `409 Conflict`.

### `POST /api/supermarkets/{id}/offers`

Creates an offer for a registered supermarket.

- Authentication: `Authorization: Bearer <api-key>`.
- Success: `201 Created`.
- Invalid ID or body: `400 Bad Request`.
- Missing or invalid credentials: `401 Unauthorized`.

Offer validation rules:

- `title`: 3 to 120 characters.
- `description`: optional, up to 500 characters.
- `discountPercent`: integer from 1 to 100.
- `startsAt` and `endsAt`: valid dates.
- `endsAt` must be later than `startsAt`.

### `GET /api/offers`

Returns active public offers.

Supported query parameters:

| Parameter | Default | Description |
| --- | --- | --- |
| `q` | empty | Searches the offer title and description |
| `city` | empty | Case-insensitive partial city filter |
| `page` | `1` | Page number |
| `limit` | `12` | Results per page, capped at 30 |

Example:

```bash
curl "http://localhost:3000/api/offers?city=Bhopal&q=fruit&page=1&limit=12"
```

The results are sorted by soonest expiry, followed by newest creation date.

## Validation and error handling

I validate all write requests at the API boundary. Invalid request bodies return a consistent response such as:

```json
{
  "error": "Please check the submitted fields.",
  "details": [
    {
      "field": "discountPercent",
      "message": "Too big: expected number to be <=100"
    }
  ]
}
```

The application uses these status codes:

| Status | Meaning |
| --- | --- |
| `201` | Resource created |
| `400` | Invalid request data |
| `401` | Missing or invalid API credentials |
| `409` | Duplicate supermarket email |
| `500` | Unexpected server-side failure |

Unexpected database failures are logged on the server, while clients receive a generic message instead of internal database details.

## Security model

The current project includes the following protections:

- API keys are generated with cryptographically secure random bytes.
- Only API-key hashes are stored in PostgreSQL.
- The raw API key is returned only once at registration.
- Offer creation verifies both the API key and the supermarket ID.
- SQL queries use parameterized values.
- Request strings and numeric values have explicit limits.
- PostgreSQL constraints protect the data even if another client bypasses the API.
- Database errors and stack traces are not returned to clients.

For a production deployment, I would additionally add HTTPS enforcement, rate limiting, supermarket verification, API-key rotation and revocation, audit logs, monitoring, and automated API tests.

## Local setup

### Requirements

- Node.js compatible with the versions supported by the installed Next.js dependencies.
- A PostgreSQL database. This project is configured for Neon.
- npm.

### Install dependencies

```bash
npm install
```

### Configure the database

Copy `.env.example` to `.env.local` and add the Neon pooled connection string:

```env
DATABASE_URL="postgresql://.../database?sslmode=require"
```

Run the SQL in `db/schema.sql` against the database to create the tables and indexes.

### Start the development server

```bash
npm run dev
```

The application will be available at:

```text
http://localhost:3000
```

### Available npm scripts

```bash
npm run dev      # Start the development server
npm run build    # Create a production build
npm run start    # Start the production server
npm run lint     # Run ESLint
```

## Example end-to-end flow

### Register a supermarket

```powershell
curl.exe -X POST http://localhost:3000/api/supermarkets `
  -H "Content-Type: application/json" `
  -d '{"name":"Green Basket","email":"offers@greenbasket.example","city":"Bhopal"}'
```

The response contains the supermarket UUID and an API key. I must save that API key because it will not be shown again.

### Publish an offer

```powershell
curl.exe -X POST http://localhost:3000/api/supermarkets/SUPERMARKET_ID/offers `
  -H "Content-Type: application/json" `
  -H "Authorization: Bearer SUPERMARKET_API_KEY" `
  -d '{"title":"Fresh fruit weekend","description":"Save on selected seasonal fruit.","discountPercent":20,"startsAt":"2026-10-22T00:00:00.000Z","endsAt":"2026-10-28T23:59:59.000Z"}'
```

The commands above use PowerShell line-continuation syntax. On macOS or Linux, replace the backtick line continuations with `\`.

### Browse offers

```bash
curl "http://localhost:3000/api/offers?city=Bhopal&q=fruit&page=1&limit=12"
```

The same endpoint is called by the GoodCart home page.

## Current scope and future improvements

The current implementation intentionally keeps the product small. It does not yet include:

- A supermarket login or dashboard.
- Offer editing or deletion.
- API-key rotation or revocation.
- Supermarket approval and verification.
- Image uploads or product categories.
- Coupon redemption tracking.
- Saved stores or user accounts.
- Rate limiting.
- Automated route and integration tests.

Possible future improvements include:

- A supermarket dashboard for managing offers.
- Fixed-amount discounts and coupon codes.
- Product images and categories.
- Sorting by discount percentage.
- Saved supermarkets and deal notifications.
- Offer views and redemption analytics.
- Audit history for supermarket and offer changes.
- Full-text search after measuring query performance.
- Automated API tests and production monitoring.

## Design goals

I kept the data model small, the public browsing flow straightforward, and the write operations protected. The application separates public browsing from authenticated publishing, validates data before it reaches the database, and uses database constraints as a second line of defense. This gives GoodCart a clear foundation that can be extended into a larger local shopping platform without adding unnecessary complexity to the initial implementation.
